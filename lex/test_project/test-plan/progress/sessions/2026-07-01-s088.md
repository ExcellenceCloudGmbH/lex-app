**Cluster 8ab landed — nested fan-out join is worker-safe (`allow_join_result` wrap).** Production crash fix: a calculation already running inside a Celery worker can fan its models out into child tasks (`CeleryTaskDispatcher.dispatch_calculation_groups` → `_dispatch_single_group` → `_handle_task_results`), then block on the children via `ResultSet.join()`. Celery **hard-forbids** `result.get()`/`ResultSet.join()` inside a worker ("Never call result.get() within a task!") unless wrapped in `allow_join_result()`. The join was unwrapped; an `is_celery_worker_process()` guard *masked* it by forcing nested calcs inline. Removing that guard (batch 7q — so nested fan-out dispatches by default, matching customer expectation) exposed the unwrapped join: a real nested `InvestmentPosting` run (5072 models, 2 tasks) crashed on the assertion, fell back to the complete-sync ladder, and re-committed already-persisted rows → duplicate-key violation. **Fix** (`_handle_task_results`): `from celery.result import ResultSet, allow_join_result` and `with allow_join_result(): rs.join(propagate=False)` — mirrors `WaitForTasks.wait_for_completion`, which already blocks under the same guard.
