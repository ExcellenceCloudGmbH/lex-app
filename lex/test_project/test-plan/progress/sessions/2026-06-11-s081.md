**Sub-cluster 8y landed — embedded-beat recovery driver (admin-visible schedule without breaking scale-to-0).** Worker recovery gains a second, interchangeable driver: alongside the always-on `recovery-supervisor` pod, an embedded-beat `lex-recovery-beat` pod runs a Celery worker with `-B` that fires the existing `sweep_dead_workers` task on a DB-driven schedule editable in the Django admin (`django_celery_beat` `DatabaseScheduler`). The pod consumes **only** its own `-Q recovery` queue, so the scan runs in-process (no warm worker needed to *detect* deaths) and the heavy recovered work re-dispatches outward to the main queue, driving KEDA — the non-circular property the supervisor already had. **Three wiring invariants make-or-break the driver and every one fails silently**, so 8y pins them as pure-logic (U) scenarios: (1) the `lex-celery-recovery-sweep` beat entry must name the registered `sweep_dead_workers` task (drift ⇒ beat enqueues a task no worker has, recovery never runs) and the sweep must stay excluded from heartbeat tracking; (2) the sweep must ride a dedicated `recovery` queue distinct from the main KEDA-watched default queue (else periodic sweeps inflate the autoscaling signal); (3) `_requeue` must route recovered tasks to their original (main) queue, never back to `recovery` (else the singleton pod re-consumes them and KEDA never scales). 8.122 pins the `beat_main` entrypoint launching `worker -B -Q recovery --scheduler django_celery_beat.schedulers:DatabaseScheduler` via the one canonical app from `supervisor._get_app()`. **Cluster 8y opened** (next-free letter after 8x; 8.116 picks up after the cluster max at 8.115).
