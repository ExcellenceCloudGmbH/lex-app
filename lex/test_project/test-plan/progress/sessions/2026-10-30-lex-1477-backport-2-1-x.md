# Batch 1az on the 2.1.x release line — backport of the LEX-1477 fix

See [1az](../../clusters/01-init/batches.md). This branch is `v2.1.11` + two commits: a
cherry-pick of `8780a119` (which adds the `/_lex/theme-relay` route) and the hardening that
mainline carries as the same batch.

Both are needed here, and for different reasons. The route is the direct cause: the deployed
frontend frames `/_lex/theme-relay`, this release line never served it, so the frame 401'd and
was handed the frame-breakout page — which sends the top window to a login whose `next` is the
path that failed. The hardening is what makes the outcome unreachable whatever 401s next: a
utility path can no longer be returned to, and a framed utility path can no longer escalate to a
top-level login at all. Either commit alone stops the tab being hijacked; only both together also
make theme sync work on 2.1.x.

Scenario IDs and the letter are deliberately identical to mainline. Letters `ae`–`ay` and
scenarios 1.303–1.414 belong to work that exists only on `lex-app-v2`, so this branch's
`max_scenario` jumps from 302 to 422 with that range unallocated here — the gap records where
those IDs live rather than reusing them for something else, and a merge in either direction is a
no-op on this batch.

One thing a 2.1.x release built from this branch does **not** carry: the frontend half. The
bundle in `lex/react/build/` at `v2.1.11` contains no theme-relay code at all (no `theme-relay`,
no `lex-theme-set`, no `lex.theme.mode`), which is itself worth recording — the relay frame that
produced the customer's symptom comes from a separately deployed, newer frontend, not from the
wheel. The client-side guards (sandboxing the relay frame, attributing `lex-auth-required` to the
dashboard frame) are in `process-admin-general-client` batch F12u and reach an instance only when
that frontend is rebuilt. The proxy changes here do not depend on them.
