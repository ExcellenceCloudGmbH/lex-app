**Diagnosed pre-existing red (13.17) → tracked as BUG-018; no framework fix applied per user directive.** Scenario `test_13_17_end_row_limit_caps_written_rows` in `test_13e_streaming_fast_export.py` asserts the documented contract: AG payload `endRow=2` against a 5-row DB must cap the streamed `.xlsx` at 2 rows. Actual: sheet carries all 5. Root-caused to `ModelExportView._normalize_ag_request` (`lex/api/views/file_operations/ModelExport.py` line ~151), which unconditionally overwrites `request_payload["endRow"] = MAX_AG_EXPORT_ROWS` (1,000,000) **before** the streaming path at `_try_stream_universal_fast_export` reads it. The per-row cap loop at line ~1229 (`if written >= end_row: break`) is therefore dead code for every call — `end_row` is always 1M. Side finding: scenario 13.7 ("`endRow` over `MAX_AG_EXPORT_ROWS` → clamped silently") is green only because the same line happens to clamp that direction too; the upward-clamp behaviour is correct but the implementation is the wrong mechanism — it clobbers rather than `min()`s. **BUG-018** added: every "export only the first N rows" affordance in the UI silently falls through to a full-table dump. Fix is a 1-line change to clamp upward while preserving user values (`request_payload["endRow"] = max(1, min(int(raw or MAX), MAX))`). Fix deferred per user directive — documenting as BUG-018 and leaving 13.17 as the one pre-existing red until a dedicated session.
