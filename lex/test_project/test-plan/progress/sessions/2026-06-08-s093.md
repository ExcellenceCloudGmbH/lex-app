Root cause: the heartbeat recovery supervisor (`lex/lex_app/celery_recovery/supervisor.py`) requeues tasks whose *worker* died, but an expired heartbeat does not prove the *task* was unfinished. A worker can persist a row's terminal `ERROR` and then be hard-killed (SIGKILL/OOM/eviction) *before* `task_postrun` deregistered it; the stale registry entry looks like a dead in-progress task, `scan_and_recover` requeues the **same `task_id`**, the re-run succeeds, and the already-concluded `ERROR` row is resurrected as `SUCCESS`. **Fix (primary, terminal-outcome guard):** before the retries/budget decision — after the existing cancellation check — `scan_and_recover` now consults two authoritative completion signals and deregisters (counts `already_finished`) instead of requeueing if either says "done": (1) a *ready* `AsyncResult` from the result backend — with `task_reject_on_worker_lost=True` a merely-lost worker never writes a result, so a ready SUCCESS/FAILURE/REVOKED proves the body ran; (2) the calculation rows themselves — every extracted `CalculationModel` row out of `IN_PROGRESS` (`_rows_already_settled`; partial / `NOT_CALCULATED` / no-rows / DB-error all degrade to "requeue" so legitimate recovery is never blocked). New helpers `_result_already_settled` / `_rows_already_settled` / `_already_finished` + a `stats["already_finished"]` counter; guard ordered before the budget branch so a finished task can never hit `_give_up` and clobber its real outcome with a spurious `ABORTED`/FAILURE. **Cluster 8w opened** (next-free letter after 8v; 8.90 picks up after the cluster max at 8.89): 8.90–8.92 result-backend signal (ready / unready / backend-error-degrades); 8.98–8.99 the OR-combination; **8.100–8.102 the integration surface** — real `scan_and_recover` with the registry boundary mocked: finished ⇒ deregister-not-requeue, unfinished-under-budget ⇒ requeue (no false-positive), finished-beats-budget-exhaustion ordering; 8.93–8.97 + 8.93b the row-state signal against real `CelerySyncCalc` rows via `E2ETestCase`.
