**Sub-cluster 3e landed — release the pre-validation rollback buffer after a successful save (v1→v2 calculate-all memory regression).** Profiling the real customer non-atomic last-period `calculate_all` (lex-app 2.0.0rc204) against lex-app-v1 showed v2 retains far more RAM per row with no leak — the differential is a per-instance constant factor. Measured with tracemalloc on a real 49-field report model: a saved+retained `LexModel` instance held **5353 B vs 1633 B** for the equivalent raw data (**3.28×**). Root cause: `LexModel` keeps **two** full-field snapshots per instance — django-lifecycle's `_initial_state` (set in `__init__`) and `_pre_validation_snapshot`, captured in the `BEFORE_SAVE` hook via `_capture_snapshot()` (`lex/core/models/LexModel.py`). The second buffer exists only so a failing `post_validation` can roll the record back (`_execute_rollback`), but it was **never released after a successful save**, so it stayed pinned on every live row for the instance's whole lifetime — pure overhead on a large calculate-all. **Fix:** null `self._pre_validation_snapshot` at the end of the successful `post_validation_hook` path (rollback can no longer happen past that point); the buffer is re-captured per save, so the failure path is unaffected. Removes ~1800 B/inst (~34% of the v2 footprint), bringing the ratio 3.28× → ~2.17×. Other v1→v2 suspects were measured and ruled out (bitemporal history is only on low-volume Plan/Period models; rc204 already streams combinations O(depth); audit LocMemCache self-bounds; DEBUG=False). **Cluster 3e** (next-free letter after 3d; 3.9 picks up after the cluster max at 3.8): 3.9 snapshot released after a successful create *and* update; 3.10 releasing on success does not weaken rollback — a later rejected update still restores the pre-save value. Reuses the existing `PostValidatedItem` model (no model change). Source: `lex/core/models/LexModel.py`. Test: `lex/test_project/tests/validation_hooks/test_3e_snapshot_lifecycle.py`.
