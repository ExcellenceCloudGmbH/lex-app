**Hotfix on PR #547 — cancelled calculations now persist ABORTED end-to-end (in-process + audit-status paths).** Session-67 wired cancel→ABORTED at the REST entry (cluster 2i) and the worker-side `CallbackTask.on_failure` (cluster 8u), but missed the third reachable surface: the in-process exception bubble through `execute_calculation_sync` and the outer `calculate_hook` except branches. Both unconditionally wrote `ERROR`, so any `CalculationCancelled` raised cooperatively from inside `calculate()` — or any worker-side `Terminated` / `SoftTimeLimitExceeded` / `WorkerLostError` / `TaskRevokedError` that propagated synchronously into the dispatching thread — corrupted the cancellation into a crash report. Companion bug: `CallbackTask._update_model_status`'s `finally` block mapped ABORTED → `audit_status="success"` ("failure if status==ERROR else success"), so the compliance row would say the cancelled calc *completed OK*. **Source fixes (2 files):** (1) `lex/core/models/CalculationModel.py` — `execute_calculation_sync`'s except branch now detects cancellation via `_is_cancellation_exception(e)` (lazy import from `lex_app.celery_tasks` to dodge the circular import the rest of this file already routes around) and picks `ABORTED` over `ERROR`; the finally block gained an `elif self.is_calculated == self.ABORTED` branch that writes the terminal audit with `audit_status="failure"` and falls back to `"Calculation cancelled by user"` when no exception text is available. The same detection in `calculate_hook` also skips `persist_error_state` on cancellation so descendants already flipped to ABORTED by the recursive cancel walk are not cascaded back to ERROR (which would corrupt the entire tree's terminal state). (2) `lex/lex_app/celery_tasks.py` — `_update_model_status`'s finally block now computes `audit_status = "success" if status == CalculationModel.SUCCESS else "failure"`, so SUCCESS is the *only* terminal state that records as success — both ERROR and ABORTED map to failure, matching the published audit semantics ("completed OK" vs "did not complete"). **Tests — three new scenarios across two clusters, mapped by surface:** in-process exception paths belong to cluster 7 (the calc state machine owns them); audit-status mapping belongs to cluster 8 (the callback machinery owns it). **Cluster 7n extended to 7.166–7.175** (next-free letter unchanged because the new surfaces extend the existing sub-cluster's contract): added `TestCluster07n_InProcessCancellationLandsAborted(E2ETestCase)` with `e2e_models = ALL_MODELS`. 7.174 patches `AtomicCalc.calculate` to raise `CalculationCancelled`, runs `execute_calculation_sync()`, asserts the row persists ABORTED on refresh — a regression here is the exact bug the user reported ("user pressed cancel but the audit shows a crash"). 7.175 patches the same plus `CalculationModel.persist_error_state`, runs `calculate_hook()`, asserts the row persists ABORTED AND `persist_error_state` was never called — pins the "do not cascade ERROR onto already-aborted descendants" contract. **Side discovery during verification:** the on-disk `TestCluster07n_Cancellation` (Session-67's 7.166–7.170) plus the new `TestCluster07n_InProcessCancellationLandsAborted` both inherited plain `django.test.TestCase` and called `AtomicCalc.objects.create(...)`, but the test-app models declare `app_label="lex_app"` so the per-test transactional DB had no matching tables — the *entire 7n DB-dependent surface* had been silently failing locally with `relation "lex_app_atomiccalc" does not exist` (verified by reproducing the same failure on the pre-existing `test_7a_atomic` infra).
