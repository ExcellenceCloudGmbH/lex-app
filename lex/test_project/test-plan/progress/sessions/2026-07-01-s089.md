**Two local-only production bugs from Report 1 (abort→resume) and Report 2 (connection storm → duplicate key), both traced by bisection to commit `4eafd0fa` (Jun 29, cluster 7q) which removed the `is_celery_worker_process()` inline-inside-worker guard from BOTH dispatch paths.** Guard was added in `40d17b3f` (2026-03-29); bisection confirmed both bugs FAIL on HEAD and PASS on `4eafd0fa^` (`93c5dd66`), and a historical sweep showed the abort test passing on 2026-05-02 / 06-01 / 06-26 and failing 2026-07-01 — matching the developer's memory that abort worked locally "at least a month ago". **The two paths need DIFFERENT worker defaults, on purpose.** (1) **Report 1 — per-instance path** (`CalculationModel.calculate_hook`): a single nested calc that dispatches its own broker task creates a message that OUTLIVES an abort. Local abort is an in-memory revoke; on server+worker restart the revoke is gone, the broker redelivers the still-unacked task, and the "cancelled" calc silently resumes. **Fix:** restore the abort-safe inline guard on the PER-INSTANCE path only — inside a worker with no async context, run inline via `execute_calculation_sync()` instead of dispatching a redeliverable task (explicit `WaitForTasks`/`FireAndForget` still dispatch; outside a worker still dispatches). (2) **Report 2 — combinatorial mixin fan-out** (`CalculatedModelMixin._dispatch_model_processing`): here the guard removal is CORRECT and kept (Option A, not Option B) so a 65k-row combinatorial calc is not serialised onto one worker slot. But its complete-sync **fallback** (`calc_and_save_sync`, run by `CeleryTaskDispatcher` when a `--concurrency 3` connection storm crashes dispatch setup) was NOT idempotent: models were dedup-resolved at T0 before dispatch (pk reset for fresh INSERT), then a sibling child task committed the row, then the fallback blind-`save()`d a second row → `duplicate key value violates unique constraint "defining_fields_<Model>"`. **Fix:** `calc_and_save_sync` now re-resolves each model via `delete_models_with_same_defining_fields()` immediately before save (mirrors `calc_and_save_streaming`) — 1 existing row → UPDATE, 0 → INSERT; fixes all four fallback call sites at once. **Stale-test flip:** 7q scenario 7.199 encoded the buggy dispatch-in-worker behaviour for the per-instance path → flipped to assert inline (abort-safe); 7q module + class docstrings updated to explain the two paths' divergent defaults. **Cluster 7r** (next free letter after 7q; 7.202 picks up after cluster-7 max 7.201), Type E: 7.202 inside worker + no context → inline via `execute_calculation_sync`, no dispatch; 7.203 inside worker + `WaitForTasks` → still dispatches; 7.204 not in worker + no context → own `WaitForTasks` + dispatch (blocks on child). **Cluster 8ac** (next free letter after 8ab; 8.139 picks up after cluster-8 max 8.138), Type I (real DB — `CombinatorialCalc.defining_fields=[region,category]` → real UNIQUE constraint): 8.139 fallback on a model whose row a sibling already committed → re-resolves → UPDATE, same pk, exactly 1 row; 8.140 fallback on a fresh model → INSERT, 1 row; 8.141 end-to-end `dispatch_calculation_groups` with `_dispatch_single_group` raising a simulated connection storm + one row pre-committed → complete-sync fallback → NO duplicate key.
