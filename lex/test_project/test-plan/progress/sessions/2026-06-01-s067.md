**Instant cancellation for in-progress Celery calculations — feature + cluster tests 7n / 2i / 8u.** Customer ask: "cancel a long-running calculation instantly when the user presses Abort." The framework's published state machine (`docs/features/processing/calculations.md`) already advertised `IN_PROGRESS → ABORTED`, but only the **startup** path in `process_admin/utils/model_registration.py` was actually wired — any IN_PROGRESS row found at boot is reset to ABORTED. There was **no live cancel path** anywhere: no REST endpoint, no flag inside `calculate_hook`, no Celery revoke. **Design chosen (Celery-only, recursive)** — sync-dispatched calcs cannot be killed in this design; the abort endpoint surfaces that explicitly as HTTP 409 with `reason=sync_calculation_not_cancellable` rather than silently lying that the click worked. Cancel is **recursive by default**: a parent cancel walks `ActiveCalculationStateStore.find_descendants(calculation_id)` and revokes every active row sharing the parent's `calculation_id`, matching the user expectation that "abort" stops the whole running tree, not just the entry point the button was attached to. **Source changes (6 files):** (1) `ActiveCalculationStateStore` — added `task_id` field per entry plus `set_task_id` / `get_task_id` / `find_descendants(calculation_id)`; `mark_in_progress` now preserves a previously-stored task_id across re-entrant hook calls (otherwise re-fire would orphan the handle the abort button needs). (2) `CalculationModel.dispatch_calculation_task()` — after `func.delay(...)` returns, captures `task_result.id` into the store keyed by `record_id`. (3) `CalculationModel.cancel(instance, *, recursive=True, reason="")` classmethod — public abort entry point, returns a dict report (`cancelled` / `cancellable` / `status` / `revoked_tasks` / `descendants_cancelled` / `reason`) the REST endpoint serialises back to the caller. Revokes are issued **before** flipping DB state so a `revoke` failure does not leave the row claiming ABORTED while a worker is still computing. (4) `_persist_aborted` / `_persist_aborted_by_entry` — mirror the ERROR-path helpers, flip `is_calculated=ABORTED`, write the cancellation reason into `calculation_error_message`/`error_message`, clear the store entry, register terminal-state persistence. (5) New `CalculationCancelled` marker exception — listed in the celery_tasks allow-list so cooperative cancel from inside calculate() code also maps to ABORTED. (6) `lex/lex_app/celery_tasks.py` — new `_is_cancellation_exception` helper (matches by class name across MRO so `TaskRevokedError` / `SoftTimeLimitExceeded` / `WorkerLostError` / `billiard.Terminated` / `CalculationCancelled` all recognised without importing celery/billiard internals); `CallbackTask.on_failure` maps those to `ABORTED` instead of `ERROR` so the audit row matches what really happened when a user cancelled. (7) `lex/api/views/model_entries/One.py.update()` — new short-circuit branch: PATCH body `{"cancel":"true"}` routes to `CalculationModel.cancel(instance, recursive=True)`, returns `202` on success or `409` on refusal, mirroring the existing `calculate=true` trigger pattern so no new URL route is required.
