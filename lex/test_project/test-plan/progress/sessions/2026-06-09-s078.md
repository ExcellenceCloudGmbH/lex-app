**Sub-cluster 1t landed — server-side cursors re-enabled in production (reload-proof `InvalidCursorName` crash).** Observed in the cluster: backend pods logged `psycopg2.OperationalError: cursor "_django_curs_..._sync_1" does not exist`, and the calculation-log panel "just loaded" forever — the log never came back from the database and no reload fixed it. **Root cause:** `lex/lex_app/settings.py` set `DISABLE_SERVER_SIDE_CURSORS = True` at **module level**, where Django never reads it — the flag is only honoured inside the per-database config dict (`connection.settings_dict`). So in deployed environments (behind the `cloud-sql-proxy-...-pooling` transaction-pooling proxy) PostgreSQL server-side cursors stayed **enabled**. Every `.iterator()` query — the permission filter backend (`filter_backends.py:232`), list views, exports — issues `DECLARE _django_curs_...` then `FETCH` in a later statement; under transaction pooling the FETCH can land on a different backend connection than the DECLARE, so the cursor "does not exist". This is deterministic per request, which is why a reload never recovered. **Fix:** after resolving `DATABASES["default"]`, loop over every alias and set `DISABLE_SERVER_SIDE_CURSORS=True` on each PostgreSQL-engine config dict (the only place Django reads it); `.iterator()` then falls back to client-side reads, which are pooling-safe. The full log still lives in `CalculationLog.calculation_log`; this only changes *how* rows are fetched. **Cluster 1t** (next-free letter after 1s; 1.169 picks up after the cluster max at 1.168): 1.169 every PostgreSQL alias carries the flag in its config dict (guards against the module-level regression); 1.170 the live `connections["default"].settings_dict` honours it on PostgreSQL (Django defaults the key to False when absent, so the old placement would surface here as False) and is engine-gated for local SQLite. Source file: `lex/lex_app/settings.py`. Test file: `lex/test_project/tests/init/test_1t_disable_server_side_cursors.py`.
