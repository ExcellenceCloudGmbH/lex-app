Incident report · IR-2026-07-16

Parallel calculation deadlock on instance 1419 — KEDA's default ScaledJob strategy never spawns the unblocking worker

Instance pfe-clone-1507-09-prod-1419 Date 2026-07-16 Impact 1 calculation stuck 5+ h, no data loss Status Root cause verified · fix in PR
TL;DR — Chained calculations block in WaitForTasks waiting for the child they just dispatched. One worker pod happened to swallow two chain links, saturating its slots so it stopped consuming messages — and KEDA's default ScaledJob strategy counted that saturated pod as the future consumer of the queued child (pending = queue − running = 1 − 1 = 0), so it never created another worker. The chain waited on a message nobody would ever read. Fix: one line — scalingStrategy: accurate.

What happened

Anne started a parallel calculation on instance 1419 around 09:00. It processes periods as a chain: each “Period addition” dispatches the next period to Celery and blocks in WaitForTasks until it completes. After two links the run went silent — no new calculation-log entry for 5+ hours. The same calculation on the same commit had worked the day before.

Timeline (worker pod …-hzs8b-7zd4x, 2026-07-16)

  • 07:10:47Task 1 received — Budget_2027_26 starts on ForkPoolWorker-2; runs its bulk-creates.
  • 07:14:10Task 1 dispatches Plan_2028_26 and blocks: WaitForTasks: waiting for 1 tasks. The same pod wins the race for the new message — Task 2 starts on ForkPoolWorker-4.
  • 07:17:19Task 2 dispatches Plan_2029_26 and blocks the same way. Both pool slots now hold blocked parents; with task_acks_late + prefetch-multiplier=1 the pod’s unacked budget is exhausted — it will never fetch another message.
  • 07:17 → 13:46+The Plan_2029_26 message sits in the Redis queue. No “Task received” is ever logged again, on any pod. KEDA re-evaluates every 5 s and declines to act (below).

Root cause — three layers interlock

  1. Application: chained parents hold their slots

    Each chain link dispatches its child and blocks in WaitForTasks. A blocked parent occupies a pool slot and keeps its message unacked (acks-late) until the child finishes — by design, indefinitely if the child never runs.

  2. Worker: a saturated pod stops consuming — but still looks “Running”

    The pod took two chain links (a race the design normally avoids via one-task-then-shutdown, but a blocked parent never finishes, so its free slot grabbed a second message). With every slot blocked, the prefetch budget is spent and the pod goes permanently deaf to the queue — while its Job status remains Running.

  3. KEDA: the default strategy credits the deaf pod as a consumer

    The ScaledJob’s default strategy computes pending = ceil(queueLength / listLength) − runningJobs. Queue = 1 (the child), running = 1 (the saturated pod) → pending = 0. Verified live in the KEDA operator log, repeating every 5 seconds for hours:

    "Number of running Jobs": 1
"Number of pending Jobs": 0
"No need to create jobs - all requested jobs already exist"

    The one worker that would unblock everything is never created. Deadlock.

Why it worked yesterday

Race timing. When each dispatched child lands on a fresh KEDA job before an existing pod grabs it, every pod holds one blocked parent, the queue count stays ahead of the running count, and the chain progresses. It only deadlocks when an existing pod with a free slot wins the race for a chain link — nondeterministic, which is what made it look flaky. It is the same race family as the 1410 incident’s “15 idle jobs” (the opposite outcome of the same KEDA-vs-existing-pod race).

Why the recovery subsystem (correctly) did nothing

The blocked tasks’ heartbeats are alive — the workers aren’t dead, they’re waiting. The dead-worker supervisor saw healthy tasks and stood down, as designed. This is a livelock, not a crash; no recovery mechanism was at fault.

The fix

scalingStrategy: default → accurate (one line)

The accurate strategy spawns a job per queued message without crediting running jobs as consumers — a dispatched child always gets a worker within one polling interval (5 s). The over-spawn case (an existing pod grabs the message first) leaves a surplus worker facing an empty queue, which the 30-second idle watchdog already terminates: the two mechanisms compose by design.

No concurrency or prefetch tuning can substitute — even a concurrency-1 pod yields queue = 1, running = 1, pending = 0 under default. The strategy is the load-bearing bug.

→ PR: LEX_TERRAFORM_MODULES #31 — fix(scaledjob): accurate scaling strategy

Immediate remediation (instance 1419)

  • Abort the stuck calculation from the UI, then delete the stuck job: kubectl delete job scaledjob-pfe-clone-1507-09-prod-1419-hzs8b, and re-run.
  • (Deleting the job alone also recovers via the heartbeat sweep, but the re-run parents can race the orphaned child message — abort-first is cleaner on a test instance.)

Verification after rollout

  • Re-run the 1419 parallel calculation: every dispatched chain link should log “Task received” on a worker within ~5 s of its dispatch line.
  • Watch job counts during the run: expect one short-lived job per chain link, surplus workers self-terminating ≤ 30 s (idle watchdog).
  • KEDA operator log should show non-zero “pending Jobs” whenever the queue is non-empty.

Follow-ups

  • Roll out per environment via Terraform after PR #31 review — the change is chart-wide, all instances inherit it on next apply.
  • Watch pod churn/cost for a week after rollout: accurate trades a possible extra short-lived pod per dispatch for deadlock-freedom; the idle watchdog bounds the waste to ~30 s per surplus pod.
  • Optional framework hardening (not required once the strategy lands): prevent a pod hosting a blocked WaitForTasks parent from fetching additional root tasks. Only worth it if churn observations argue for it.
