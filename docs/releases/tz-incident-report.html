Incident Report · Internal

Naive-datetime convention break: why timestamps shifted after upgrading, and the fix going forward

Date: 16 Jul 2026 Trigger: customer ticket (datetime fields ±1h, equality filters broken) Root cause: f622c9c · PR #635 · shipped v2.0.0rc212

1What the customer is seeing

Project code creates datetime values naively — e.g. datetime(year, 12, 31) for an output_date — and expects to read back exactly YYYY-12-31 00:00. After upgrading to 2.1.3:

  • rows that existed before the upgrade read back as YYYY-12-30 23:00;
  • rows created after the upgrade read back correctly;
  • equality filters (output_date = datetime(Y,12,31)) stopped matching the old rows;
  • after reverting the upgrade, the old rows are correct again — but rows created while on 2.1.3 now read YYYY-12-31 01:00.

All four observations — including the shift being exactly one hour (December = Berlin winter offset) and it flipping direction on revert — are explained by a single root cause.

2Why this started happening

On instances where USE_TZ=False (our default/GCP deployment targets), the framework stores naive datetimes. What a naive value means is decided by settings.TIME_ZONE — because under USE_TZ=False, Django sets it as the PostgreSQL connection timezone, and datetime columns are timestamp with time zone. Naive values are interpreted in that zone on write and rendered back in it on read.

Commit f622c9c (PR #635, merged 26 Jun 2026, first shipped in v2.0.0rc212) changed exactly that setting: 

- TIME_ZONE = "Europe/Berlin"
+ TIME_ZONE = "Europe/Berlin" if USE_TZ else "UTC"   # → UTC on default/GCP

It was a correct fix for a real bug: django-celery-beat's scheduler hard-codes naive==UTC, so with Berlin-based storage the recovery sweep never became due and future-dated activations fired hours late. What it missed is the side effect: changing TIME_ZONE under USE_TZ=False re-interprets every naive timestamp already in the database. Data written before rc212 was stored as Berlin wall-clock instants; the new UTC connection renders those same instants one/two hours earlier. No data was lost or corrupted — the stored instants never moved — but the naive values project code reads and compares changed.

ObservationMechanism
Old rows → 23:00 on 2.1.3Written under Berlin connection (00:00 Berlin = 23:00 UTC instant); read under the new UTC connection.
New rows → 00:00 on 2.1.3Written and read under UTC — self-consistent.
Revert: old rows → 00:00Berlin connection restored; old instants render as Berlin wall again.
Revert: 2.1.3-era rows → 01:00Those instants are 00:00 UTC; rendered under Berlin → 01:00.

This also reframes the earlier “timestamps display 2h off” ticket: both tickets are the same convention change seen from different sides (display vs. stored naive values). Any instance that upgraded across the rc211 → rc212 boundary with pre-existing data has this skew — 2.1.3 is simply when this customer crossed it.

3The fix going forward

The constraint that forced UTC is going away: we are retiring celery-beat (recovery moves to the always-on supervisor; future-edit activations move to the global scheduler — neither reads naive datetimes as UTC). That lets us restore the original convention that all existing customer data and project code were built on. The fix, merged as PR #658, is deliberately opt-in and changes nothing by default:

  1. LEX_TIME_ZONE env override. Default behavior is byte-identical to today. An instance restores the pre-rc212 convention by setting LEX_TIME_ZONE=Europe/Berlin — only once it is beat-free.
  2. Truthful timestamps in every mode. The API labels naive values with their real meaning: a trailing Z when the convention is UTC (today, unchanged), or the real DST-aware offset (+01:00 winter / +02:00 summer) when an instance runs the Berlin convention. Browsers render the intended wall-clock time either way — the frontend needs no changes.
  3. Time-travel follows the convention. as_of query anchors are normalized into the same naive convention the database compares against, so historical queries never shift by the UTC offset.

What we deliberately did not ship: an automatic data migration. Rows written during an instance's UTC era (rc212 → the flip) are a bounded, identifiable set. At flip time they need a one-off, DST-aware repair — UPDATE … SET col = (col AT TIME ZONE 'UTC') AT TIME ZONE 'Europe/Berlin' — run per instance with a backup and a dry check. Doing this operationally, per instance, is safer than a blanket migration that cannot know each instance's upgrade date.

Rollout per instance

  1. Instance becomes beat-free (supervisor recovery + global scheduler).
  2. One-off era repair of the UTC-window rows (ops, backed up, dry-checked).
  3. Set LEX_TIME_ZONE=Europe/Berlin, restart.
  4. Verify: old rows render their original wall-clock, equality filters match, UI display correct.

Immediate guidance for the affected customer: staying on the reverted version is correct for now — their pre-upgrade data is consistent again. The only residual is the small set of rows created while on 2.1.3 (now reading +01:00); those can be corrected with the same one-off statement bounded to that window. They should upgrade again once the rollout above reaches their instance.

4Verification

  • Batch 12j (scenarios 12.46–12.48): DST-aware per-value offsets; UTC default keeps the established Z contract byte-identical; as_of convention normalization.
  • Existing timezone gates (12g, 5m) all green — proving today's default behavior is untouched.
  • Full regression across serializers, history, audit logging, and CRUD API: 277 pass / 0 fail.
